# Travel Booking Engine

## Цель проекта
Данный проект разработан для демонстрации навыков проектирования и реализации распределенной микросервисной архитектуры в условиях высоких нагрузок. Главная цель — создание надежной системы бронирования авиабилетов, обеспечивающей строгую консистентность данных между независимыми сервисами без применения монолитных подходов и распределенных блокировок. Проект реализует паттерн Saga (Orchestration), событийно-ориентированную архитектуру (Event-Driven Architecture) и полностью асинхронное взаимодействие через брокер сообщений.

## Архитектура системы
Проект состоит из набора независимых микросервисов:

1. **API Gateway (Порт 8080):** Единая точка входа. Отвечает за маршрутизацию запросов и защиту от перегрузок (Rate Limiting).
2. **Flight Aggregator (Порт 8081):** Агрегатор рейсов. Реализует поиск билетов, расчет сложных маршрутов ("умные стыковки") и динамическое ценообразование. Использует In-Memory кэширование (Caffeine) для снижения нагрузки на БД. Защищен паттерном Circuit Breaker (Resilience4j).
3. **Booking Orchestrator (Порт 8082):** Центральный узел обработки бронирований. Сохраняет состояние транзакций в PostgreSQL с использованием реактивного драйвера R2DBC и механизма оптимистичной блокировки (@Version). Управляет процессом распределенной транзакции (Saga), координируя действия других сервисов через Kafka.
4. **Profile Service (Порт 8086):** Сервис профилей и антифрод-система. Валидирует ИИН пассажиров на наличие в черных списках. Также отвечает за прослушивание финальных событий оплаты для имитации отправки SMS-уведомлений.
5. **Loyalty Service (Порт 8083):** Сервис лояльности. Асинхронно обрабатывает начисление и заморозку бонусов, слушая соответствующие топики брокера сообщений.
6. **Payment Gateway (Порт 8084):** Платежный шлюз. Асинхронно обрабатывает транзакции по банковским картам по командам из Kafka.
7. **Shared Core:** Общий модуль, содержащий DTO, интерфейсы команд и событий для строгой типизации контрактов взаимодействия между сервисами.

## Стек технологий
* **Язык программирования:** Java 21
* **Фреймворк:** Spring Boot 3.3.4 (Spring WebFlux, Spring Web)
* **База данных:** PostgreSQL 15, Spring Data R2DBC (реактивный доступ к данным)
* **Брокер сообщений:** Apache Kafka, Zookeeper
* **Инфраструктура:** Docker, Docker Compose
* **Паттерны отказоустойчивости:** Resilience4j (Circuit Breaker)
* **Кэширование:** Caffeine Cache
* **Наблюдаемость (Observability):** Micrometer (Distributed Tracing), Actuator, Prometheus
* **Документация:** Swagger (OpenAPI 3.0)
* **Управление сборкой:** Gradle

## Результаты работы проекта (Демонстрация распределенной транзакции)

Процесс бронирования запускается REST-запросом. На этом этапе Booking Orchestrator выполняет синхронную проверку клиента через Anti-Fraud сервис и, в случае успешной валидации, фиксирует первичный статус брони в базе данных, после чего передает управление брокеру сообщений.

### 1. Инициирование бронирования
Выполнение REST-запроса через PowerShell:
```powershell
Invoke-RestMethod -Uri "http://localhost:8082/v1/bookings/hold?flightId=1&seatNumber=12B&iin=111111111111" -Method Post
```

Синхронный ответ от API (указывающий на старт транзакции):
```text
id         : 3
flightId   : 1
seatNumber : 12B
status     : NEW
createdAt  :
fareType   :
version    : 0
```

### 2. Асинхронная обработка (Saga Pattern)
Сразу после быстрого ответа пользователю микросервис Booking Orchestrator отправляет команды в Kafka. Микросервисы Loyalty Service и Payment Gateway последовательно перехватывают эти команды, производят заморозку бонусов и списание средств, возвращая события успеха. 

В случае, если клиент использует скомпрометированный ИИН (находится в реестре должников), система прерывает процесс бронирования еще на стадии первичной проверки и отменяет транзакцию.

### 3. Финальное состояние базы данных
Итоговое состояние таблицы `bookings` в PostgreSQL после успешного завершения всего цикла Saga-транзакции всеми микросервисами:

```text
 id | flight_id | seat_number |        status         
----+-----------+-------------+-----------------------
  1 | 1         | 12A         | REJECTED_BY_ANTIFRAUD 
  6 | 1         | 14C         | TICKET_ISSUED         
  4 | 1         | 14C         | TICKET_ISSUED         
  5 | 1         | 14C         | TICKET_ISSUED
```

Как видно из дампа базы данных:
* Бронирование `ID 1` было успешно заблокировано антифрод-системой (REJECTED_BY_ANTIFRAUD).
* Бронирования `4`, `5` и `6` успешно прошли асинхронный цикл оплаты и начисления бонусов через Kafka, получив финальный статус выписанного билета (TICKET_ISSUED).
